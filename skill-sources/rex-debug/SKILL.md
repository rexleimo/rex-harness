# Rex Debug 候选规则

Required sequence:
1. Read the current Command and reproduce the declared failure before changing code.
2. Build a red-capable feedback loop before forming any root-cause theory.
3. Separate facts, hypotheses, falsifiers, and receipts in one bounded diagnostic loop.
4. Stop with a typed evidence handoff or blocked/no-op result; do not select another Provider.

## 1. 启动条件与 Command 边界

只有在 Capability 已经激活且当前 Command 明确后才开始。先完成当前 Command 要求的证据产物；若 Command 只要求复现、证据分类、根因证明或回归定义，就不要实现修复、扩大任务范围或调用下一个 Provider。

本技能下列判据全部以"当前 Command 要求的证据产物"为交付面：它们收紧证据的形状，不新增交付状态词。

## 2. 可复现证据与认知分层

用最小稳定步骤复现失败，并记录输入、环境、实际结果和期望结果。沿数据流和控制流收集可追溯证据；将已验证的事实、待检验的假设和未验证的猜测分开标注，不能因日志中的同时出现或相关变化直接认定因果。

### 2.1 反馈回路优先

没有能为这个缺陷变红的回路时，不进入假设阶段：**先造回路，再谈根因**。发现自己正在靠读代码构建理论，就是本技能要拦下的那次失败。

构造手段按此顺序尝试，并在证据里记录已试过的路径与被排除的原因：

1. 在能触达缺陷的任一 seam 上的失败测试（单元、集成、e2e）。
2. 对运行中的 dev server 发 curl / HTTP 脚本。
3. CLI 调用固定 fixture，把 stdout 与已知良好快照做 diff。
4. headless 浏览器脚本驱动 UI，并断言 DOM、console、network。
5. 重放已捕获的 trace：把真实请求、载荷或事件日志落盘，再单独驱动该代码路径。
6. 一次性最小 harness：只起一个服务、依赖被 mock，单次函数调用即可触达缺陷路径。
7. 属性或模糊循环：缺陷表现为"有时输出错"时，跑足够多次随机输入以定位失败形态。
8. 二分 harness：缺陷出现在两个已知状态（提交、数据集、版本）之间时，做成可被 `git bisect run` 驱动的自动化。
9. 差分回路：同一输入分别跑新旧版本或两套配置，比较输出。
10. 人在环脚本：最后手段。若确实需要人点击，用结构化脚本驱动该人，让产出回流成可重放的记录，而不是散落的口头描述。

### 2.2 回路质量判据（四项逐项自报告，缺一不得进入 §3）

模型必须在证据里逐项声明并给出依据，而不是笼统声称"能复现"：

- `red-capable`：回路驱动到真实缺陷代码路径，并断言**用户描述的那个症状**；它会因本缺陷变红、因修复变绿。"跑起来没报错"不算。
- `deterministic`：每轮结论一致。抖动缺陷按 §2.4 转化为"复现率已足够高"。
- `fast`：秒级，而不是分钟级。
- `agent-runnable`：可无人值守执行；人在环只通过被记录的结构化脚本。

收紧回路本身属于任务：更快（缓存 setup、跳过无关初始化、缩小测试范围）、信号更锐（断言具体症状而非"没崩"）、更确定（钉时间、seed RNG、隔离文件系统、冻结网络）。一个 30 秒的抖动回路几乎不比没有回路好多少；一个 2 秒的确定回路才是诊断能力。

### 2.3 回路要留下执行证明

上述每项都要引用一次真实执行回执：写出命令与参数、退出码，以及它变红的输出片段（抖动缺陷则记变红次数与总轮数）。声称"已经跑过"但没有回执的回路，不计为完成 §2。

### 2.4 非确定性缺陷

目标不是拿到一次干净复现，而是**把复现率抬到可诊断**：循环触发多次、并行、加压、缩窄时间窗、注入延迟。复现率低到无法判定时继续抬率，不转为猜测。

### 2.5 确实造不出回路时

停手并显式声明，列出已尝试的构造路径，向当前 Command 返回 `blocked`，同时请求三选一输入：(a) 能复现的环境访问；(b) 已捕获且已脱敏的工件（HAR、日志转储、core dump、带时间戳的录屏）；(c) 添加临时插桩的许可。不得在没有回路的情况下进入假设阶段。

## 3. 根因区分与最早偏差

每轮只设计一个控制变量清晰的最小诊断实验，并预先说明各结果会如何区分根因解释。定位最早发生语义偏差的位置，而非先修复下游症状；证据不足时继续收集复现和观测，不以猜测为由进行批量、跨层或不可逆修改。

### 3.1 假设成组且可证伪

一次生成 3 到 5 个排序假设，再开始检验——单假设生成会锚定在第一个看似合理的想法上。每个假设必须写成可证伪的预测：

> 若 `<X>` 是原因，则改变 `<Y>` 会让缺陷消失 / 改变 `<Z>` 会让它恶化。

写不出预测的假设是感觉，要么丢掉，要么磨利它。进入 §4 前把排序清单呈现给人类一次，但**不阻塞**：领域知识常常能立刻重排（"我们刚部署了 #3 的改动"）或指出已被排除的假设；用户不在场就按自己的排序继续。

### 3.2 探针必须映射到预测

每个探针都要对应 §3.1 中的某一条具体预测，且一次只改一个变量。工具偏好：环境支持时的 debugger / REPL 检查 > 能区分假设的边界定点日志 > 禁止"全量打日志再 grep"。

### 3.3 性能类缺陷另走一支

性能退化通常不该靠日志定位：先建立基线测量（计时 harness、profiler、query plan），再做二分。**先测量，后修改。**

## 4. 回归闭环与证据交付

根因已获证据支持后，定义修复前失败、修复后通过且结果确定的回归检查。交付 `failure-reproduced`、`root-cause-evidenced`、`regression-check-recorded` 中当前 Command 所需的状态，并为每项附上真实命令、日志、代码位置或测试引用；宿主要求 `AIOS_REX_EVIDENCE` 时，仅在结尾输出当前 `activationId` 的恰好一个证据信封。

### 4.1 只在正确的 seam 上锁缺陷

回归测试只有当存在**能重现真实缺陷模式的正确 seam** 时才有意义。若唯一可用的 seam 太浅（缺陷需要多调用方而只有单调用方入口，或单元层无法复现触发链），在那里写测试给出的是假信心。此时**"不存在正确 seam"本身就是本轮的发现**：把它作为一项记录进 `regression-check-recorded` 证据并说明架构原因，不得为了"有个测试"而写浅测试。

### 4.2 假红要自证

如果这个红是靠改动代码或夹具强制出来的，先与 pristine 副本 `diff`，证明那处改动确实落地，再相信这个红。

## 5. 插桩与工件卫生

- 每条调试日志带唯一前缀（例如 `[DEBUG-a4f2]`），使清理退化为一次 grep：无前缀的日志会存活，有前缀的才会被清干净。交付前执行该 grep，并把"零命中"作为执行回执。
- 一次性原型要么删除，要么移入明确标注的调试位置，不得留在正常路径上。
- 展示命令、输出与捕获工件之前先脱敏（密钥一律写作 `<REDACTED>`），让凭据走环境变量而不是进入被展示的内容；只引用承载信号的那几行。**若脱敏后的输出不足以诊断，就明说并向用户索取，不要凭未脱敏的猜测继续。**

## 6. 结论回流

被证明正确的那个假设要写进 commit / PR 正文（一句话即可）：下一个调试者应当能从代码历史里学到它，而不是重走一遍回路。

### S2 feedback loop boundary

每轮诊断必须形成一个可回放的 loop：`observation -> hypothesis -> falsifier -> receipt -> next action`。没有新的观察或 receipt 时不得重复猜测；同样地，当两轮之间回路质量（§2.2）、复现率（§2.4）或假设清单（§3.1）都没有变化时，也按没有新观察处理。失败不可复现时返回 `blocked`，而不是把日志相关性写成根因。已经完成且没有新行为差异的请求返回 `no-op-recorded`，停止在当前 Command。
